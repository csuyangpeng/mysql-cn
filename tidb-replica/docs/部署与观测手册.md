# 部署与观测手册

配套文档：

- [../README.md](../README.md)：部署与演练命令
- [主备容灾总体方案.md](主备容灾总体方案.md)：设计决策与验证记录

本文按“操作 → 观测 → 通过标准 → 失败排查”组织，适合现场照做。
约定：主站 `10.18.1.27`，备站 `10.18.1.28`，VIP `10.18.1.100`，
网卡 `ens3`，仓库路径 `/home/sder/mysql-cn/tidb-replica`。

## 0. 适用场景

- **全新环境**：从第 1 步开始。
- **在当前两台上重来**：先执行下面的重置，再回到第 1 步。

```bash
# 1) 先停 .28 的 keepalived 释放 VIP，再停 .27
ssh sder@10.18.1.28 'sudo systemctl stop keepalived'
sudo systemctl stop keepalived

# 2) 停容器（先主后备）
cd /home/sder/mysql-cn/tidb-replica
./scripts/stop-cluster.sh

# 3) 旧数据改名保留，不要直接删
sudo mv primary/data primary/data.bak.$(date +%Y%m%d%H%M%S)
ssh sder@10.18.1.28 'cd /home/sder/mysql-cn/tidb-replica && sudo mv secondary/data secondary/data.bak.$(date +%Y%m%d%H%M%S)'
```

观测：

```bash
docker ps --format '{{.Names}}' | grep tidb || echo "no tidb containers"
ss -lntp | grep -E ':(2379|4000|8300|10080|20160)\b' || echo "ports free"
ip -brief addr show | grep -w 10.18.1.100 || echo "VIP released"
```

通过标准：无 TiDB 容器、端口全空、VIP 不在任何一台。

## 1. 步骤总览

| # | 阶段 | 操作位置 | 关键观测 |
|---|---|---|---|
| 2 | 部署前检查 | 两站 | 镜像、端口、VIP、网卡、时间 |
| 3 | 启动备站 | .28 | 4 容器 Up、`/status` 200、store Up |
| 4 | 启动主站 | .27 | 同上 |

| 8 | VIP 接入测试 | 客户端/应用 | `10.18.1.100:4000` 可读写 |

## 2. 部署前检查

```bash
# 两站分别执行
hostname -I | grep -w 10.18.1.27        # .28 上换成 10.18.1.28
ip -brief link show ens3
docker --version && docker compose version
keepalived --version
docker images --format '{{.Repository}}:{{.Tag}}' \
  | grep -E 'pd:v7.5|tikv:v7.5|ticdc:v7.5|tidb-replica:local'
ss -lntp | grep -E ':(2379|4000|8300|10080|20160)\b' || echo "ports free"
ping -c1 -W1 10.18.1.100 >/dev/null 2>&1 && echo "VIP 被占用" || echo "VIP free"
timedatectl | grep -E 'System clock|NTP'
```

通过标准：5 个镜像齐全；5 个端口全空；VIP 未被占用；两端时间同步正常。

失败排查：网卡不是 `ens3` 时，修改 `scripts/keepalived-master.conf`、
`scripts/keepalived-backup.conf` 的 `interface` 与 `virtual_ipaddress`。

## 3. 启动备站（.28）

```bash
cd /home/sder/mysql-cn/tidb-replica/secondary
docker compose up -d
```

观测：

```bash
docker compose ps
curl -s -o /dev/null -w 'tidb=%{http_code}\n' http://127.0.0.1:10080/status
curl -s -o /dev/null -w 'pd=%{http_code}\n'   http://127.0.0.1:2379/pd/api/v1/health
curl -s http://127.0.0.1:2379/pd/api/v1/stores | grep -o '"state_name"[^,]*'
```

通过标准：`pd/tikv/ticdc/tidb-secondary-sql` 四个容器 Up，TiDB 为 `healthy`；
`tidb=200`、`pd=200`；store 为 `"state_name": "Up"`。

首次 bootstrap 需要 1–3 分钟，期间 TiDB 显示 `health: starting` 属正常。

失败排查：

```bash
docker logs tidb-secondary-sql 2>&1 | tail -30
docker logs tidb-secondary-tikv 2>&1 | tail -20
docker logs tidb-secondary-pd 2>&1 | tail -20
```

## 4. 启动主站（.27）

```bash
cd /home/sder/mysql-cn/tidb-replica/primary
docker compose up -d
```

观测与通过标准同第 3 步（容器名换成 `tidb-primary-*`）。

也可以一次性启动两站：

```bash
cd /home/sder/mysql-cn/tidb-replica
./scripts/start-cluster.sh
```

脚本会先启 .28、再启 .27，并等待两端 `/status` 返回 200。

## 5. 建立正向同步（.27）

```bash
cd /home/sder/mysql-cn/tidb-replica/scripts
./setup-replication.sh
```

观测：

```bash
docker exec tidb-primary-ticdc /cdc cli changefeed query \
  -c primary-to-secondary --server=http://127.0.0.1:8300 --simple
```

通过标准：`"state": "normal"`；`checkpoint_tso` 持续增大；
`checkpoint_time` 与当前时间相差几秒内。

失败排查：

```bash
# 去掉 --simple 看 error 字段
docker exec tidb-primary-ticdc /cdc cli changefeed query \
  -c primary-to-secondary --server=http://127.0.0.1:8300

# 备站 4000 是否可达
curl -s -o /dev/null -w '%{http_code}\n' http://10.18.1.28:4000
```

## 6. 数据同步测试

在主库执行（使用单位的国产 SQL 客户端或业务应用）：

```sql
CREATE DATABASE IF NOT EXISTS dr_test;
CREATE TABLE dr_test.t1(id INT PRIMARY KEY, name VARCHAR(50));
INSERT INTO dr_test.t1 VALUES (1,'alpha'),(2,'beta'),(3,'gamma');
```

在备库查询：

```sql
SELECT * FROM dr_test.t1 ORDER BY id;
```

观测延迟：

```bash
docker exec tidb-primary-ticdc /cdc cli changefeed query \
  -c primary-to-secondary --server=http://127.0.0.1:8300 --simple
```

通过标准：备库 3 行与主库一致；`checkpoint_time` 持续追近当前时间。

## 7. 部署 Keepalived（先 .27，后 .28）

```bash
# .27
cd /home/sder/mysql-cn/tidb-replica/scripts
sudo ./deploy-keepalived.sh master

# .28
ssh sder@10.18.1.28 \
  'cd /home/sder/mysql-cn/tidb-replica/scripts && sudo ./deploy-keepalived.sh backup'
```

观测 .27：

```bash
systemctl is-active keepalived
sudo cat /run/tidb-dr-state                  # 期望 MASTER
ip -4 addr show ens3 | grep 10.18.1.100      # 期望有
sudo /etc/keepalived/check_tidb.sh; echo $?  # 期望 0
journalctl -u keepalived -n 20 | grep -E 'MASTER|FAULT'
```

观测 .28：

```bash
sudo cat /run/tidb-dr-state                  # 期望 BACKUP
ip -4 addr show ens3 | grep 10.18.1.100 || echo "no vip"
```

通过标准：VIP 只在 .27；.27=MASTER、.28=BACKUP；两端健康检查都返回 0。

失败排查：

| 现象 | 处理 |
|---|---|
| `SECURITY VIOLATION` | 确认 `global_defs` 中有 `enable_script_security` 与 `script_user root` |
| VIP 不出现 | `journalctl -u keepalived -n 50`；确认脚本路径与权限 |
| 角色反了（.28 先成 MASTER） | 停 .28 keepalived，让 .27 接管后再启 .28 |
| 健康检查返回 1 | 分别执行三段 `curl` 定位是 TiDB、PD 还是 TiKV |

## 8. VIP 接入测试

```bash
curl -s -o /dev/null -w 'vip=%{http_code}\n' http://10.18.1.100:10080/status
```

用客户端连 `10.18.1.100:4000`：

```sql
INSERT INTO dr_test.t1 VALUES (4,'via-vip');
SELECT * FROM dr_test.t1 ORDER BY id;
```

通过标准：`vip=200`；经 VIP 写入成功；该行在 .28 备库可见。

## 9. 故障切换测试

```bash
# .27 注入故障
docker stop tidb-primary-sql
```

观测（约 3–10 秒内）：

```bash
# .27
sudo cat /run/tidb-dr-state                  # 期望 FAULT

# .28
sudo cat /run/tidb-dr-state                  # 期望 MASTER
ip -4 addr show ens3 | grep 10.18.1.100      # 期望出现
curl -s -o /dev/null -w 'vip=%{http_code}\n' http://10.18.1.100:10080/status
```

在 .28 执行切换并记录位点：

```bash
cd /home/sder/mysql-cn/tidb-replica/scripts
sudo ./failover.sh
sudo cat /var/lib/tidb-dr/failover-tso       # 期望一串数字
```

在 .28 写入故障期间数据（如 id=5），确认成功。

通过标准：VIP 30 秒内漂到 .28；`failover-tso` 已写入；.28 可写。

## 10. 恢复旧主与反向同步

```bash
# .27 恢复 TiDB
ssh sder@10.18.1.27 'docker start tidb-primary-sql'
```

观测 .27：`/status` 返回 200，但状态仍为 BACKUP，且没有 VIP。

在 .28 建立反向同步：

```bash
cd /home/sder/mysql-cn/tidb-replica/scripts
sudo ./recovery.sh
```

观测：

```bash
docker exec tidb-secondary-ticdc /cdc cli changefeed query \
  -c secondary-to-primary --server=http://127.0.0.1:8300 --simple
```

在 .27 查询故障期间写入的数据（如 id=5）。

通过标准：反向 feed `normal`；故障期间数据在 .27 可见。

## 11. 回切测试

先停业务写入，然后在 .28：

```bash
cd /home/sder/mysql-cn/tidb-replica/scripts
sudo ./switchback.sh
```

观测：

```bash
# VIP 回到 .27，.28 为 BACKUP
ip -4 addr show ens3 | grep 10.18.1.100
ssh sder@10.18.1.28 'sudo cat /run/tidb-dr-state'

# 只剩正向 feed
docker exec tidb-primary-ticdc /cdc cli changefeed list \
  --server=http://127.0.0.1:8300
ssh sder@10.18.1.28 \
  'docker exec tidb-secondary-ticdc /cdc cli changefeed list --server=http://127.0.0.1:8300'
```

经 VIP 写一条新数据（如 id=6），确认 .28 可见。

通过标准：VIP 在 .27；.28=BACKUP；只有 `primary-to-secondary`；
新数据同步到 .28。

## 12. 异常速查

| 现象 | 先看 |
|---|---|
| TiDB 长时间 `starting` | `docker logs <tidb容器>`；TiKV store 是否 Up |
| changefeed 不 normal | `changefeed query` 的 `error`；备站 4000 是否可达；GC |
| 健康检查返回 1 | 分别跑 `/status`、`/pd/api/v1/health`、`/pd/api/v1/stores` |
| VIP 不漂移 | `journalctl -u keepalived`；`weight` 是否误配；unicast 对端 |
| 回切被拒绝 | 反向 feed 的 `checkpoint_tso` 是否 ≥ `TSO_CUT`；是否还有写入 |
| 两端不一致 | 是否同时存在两个方向的 feed；比对 `checkpoint_time` |

## 13. 验收清单

- [ ] 两站各 4 容器 Up，`/status` 200，PD health 200，TiKV store Up
- [ ] GC 保留时间为 `24h`（`SELECT @@global.tidb_gc_life_time`）
- [ ] 正向 feed normal，数据延迟 < 5s
- [ ] VIP 只在 .27，`10.18.1.100:4000` 可读写
- [ ] 停 .27 TiDB 后 VIP 30s 内漂到 .28，备站可写
- [ ] 切换 TSO 已写入 `/var/lib/tidb-dr/failover-tso`
- [ ] 旧主恢复后保持 BACKUP，不抢 VIP
- [ ] 反向 feed 以切换 TSO 创建，故障期数据补齐
- [ ] 回切后 VIP 回 .27，只保留一个正向 feed
- [ ] 回切后新写入可同步到 .28

## 14. 时间预期

| 动作 | 预期 |
|---|---|
| 首次启动单站 | 1–3 分钟 |
| TiDB 停止后 VIP 漂移 | 3–10 秒 |
| changefeed 建立 | < 10 秒 |
| 正常同步延迟 | 秒级（同一内网） |
| 反向同步追平 | 取决于故障期间写入量，通常秒级到分钟级 |
