# TiDB 两节点主备容灾总体方案（VIP 接入）

> 适用环境：10.18.1.27（主站）、10.18.1.28（备站）
> 版本：TiDB v7.5.0（容器化，单 PD + 单 TiKV + 单 TiDB + 单 TiCDC）
> 接入方式：Keepalived VIP `10.18.1.100:4000`
> 文档状态：待评审

## 1. 背景与目标

### 1.1 背景

现有 `tidb-replica` 是两节点容器化 TiDB 实验环境。两站各部署一套完整但相互独立的
TiDB 集群，通过 TiCDC 做单向增量同步，目标是用一个 VIP 对应用屏蔽站点切换。
上一轮已搭出骨架，但存在网卡、VRRP 单播、VIP 抢占、回切丢数据等问题，未形成可演练闭环。

### 1.2 目标

| 目标 | 说明 |
|---|---|
| 统一接入 | 应用只连接 `10.18.1.100:4000`，不感知后端站点 |
| 故障切换 | 主站 TiDB 不可用时，VIP 自动漂移到备站，RTO ≤ 30s |
| 数据同步 | 正常态主 → 备增量同步；切换后备 → 主反向补齐 |
| 可回切 | 原主恢复并追平后，可人工回切，回切过程不丢数据 |
| 可演练 | 全流程有脚本、有验收标准、可重复执行 |

### 1.3 非目标（明确不做）

- 站内高可用：每站只有 1 个 TiKV、1 个 PD，站内无副本，不具备单机故障容忍
- 自动选主/自动提升：没有仲裁与 fencing，切换由 Keepalived + 人工确认完成
- 双活/双写：备站正常态不接受业务写入
- RPO = 0：TiCDC 为异步复制，故障瞬间未同步的数据无法保证

### 1.4 工具链约束（国产化）

- 数据库只用 TiDB，不引入 MySQL 数据库。
- 运维链路不依赖 MySQL 客户端：
  - 健康检查：TiDB 自带的 HTTP 状态接口 `http://127.0.0.1:10080/status`
  - TSO 获取、同步状态：TiCDC 原生 CLI `/cdc cli`
  - 集群状态：PD 原生 CLI `/pd-ctl`
  - GC 保留时间：TiDB 初始化 SQL 自动执行（已实现）
  - 数据校验：单位统一的国产 SQL 客户端或业务应用
    （本环境镜像未内置 Dashboard，`/dashboard` 实测返回 404）
- TiCDC 的 `sink-uri` 写作 `mysql://...` 是它对 MySQL 协议下游的固定 URI 格式，**下游实际是 TiDB**，
  不代表使用 MySQL 数据库或 MySQL 客户端。

## 2. 总体思路

一句话：**两套独立集群 + TiCDC 单向异步复制 + Keepalived 维护 VIP + 以“切换时刻 TSO”为锚点做反向补齐。**

```
                    应用（只认 VIP）
                          │
                10.18.1.100:4000
                          │
                 ┌────────┴────────┐
                 │   Keepalived    │  VRRP 单播，nopreempt
                 │  .27 ⇄ .28      │  VIP 同一时刻只在一个站点
                 └────────┬────────┘
                          │
        ┌─────────────────┴──────────────────┐
        │ 主站 10.18.1.27                    │ 备站 10.18.1.28
        │ tidb-primary-sql :4000             │ tidb-secondary-sql :4000
        │ tidb-primary-pd  :2379             │ tidb-secondary-pd  :2379
        │ tidb-primary-tikv:20160            │ tidb-secondary-tikv:20160
        │ tidb-primary-ticdc:8300 ──正向──▶  │ tidb-secondary-ticdc:8300
        │                    ◀──反向（回切）──│
        └────────────────────────────────────┘
```

核心设计点：

1. **站点独立**：两套集群互不共享 PD/TiKV，跨站只通过 TiCDC 传递变更，避免跨站 Raft 对网络和延迟的强依赖。
2. **VIP 与数据角色解耦**：Keepalived 根据本机 TiDB 健康状态决定 VIP 归属；VIP 在谁身上，谁就是当前主站。
3. **不回抢**：`nopreempt` + 两端 `state BACKUP`，原主恢复后不会自动把 VIP 抢回去，避免流量切回旧数据。
4. **切换即记锚点**：故障切换时记录 `TSO_FAILOVER`，回切时以它为 `--start-ts` 建反向 changefeed，补齐故障期间备站的全部写入。
5. **空库起步**：TiCDC 只做增量，不做全量。备站必须从空库开始，或在建 changefeed 前用 Dumpling/BR 做一次全量并指定快照 TSO。

## 3. 组件与职责

| 组件 | 位置 | 职责 | 关键参数 |
|---|---|---|---|
| TiDB | 两站各 1 | SQL 层，对外 4000 | `--store=tikv --path=pd:2379` |
| PD | 两站各 1 | 元数据、TSO、调度 | 2379 客户端 / 2380 内部 |
| TiKV | 两站各 1 | 数据存储，单副本 | 20160 |
| TiCDC | 两站各 1 | 变更捕获与投递 | 8300 |
| Keepalived | 两站宿主机 | 维护 VIP、健康检查 | VRRP vrid 51，单播 |
| Docker | 两站宿主机 | 容器编排 | compose v2 |

容器命名固定为 `tidb-{primary|secondary}-{pd|tikv|sql|ticdc}`，脚本依赖这些名字。

### 3.1 端口规划

| 端口 | 用途 | 暴露范围 | 说明 |
|---|---|---|---|
| 4000 | TiDB SQL | 0.0.0.0 | 应用接入 + 跨站 CDC sink，必须互通 |
| 10080 | TiDB 状态/健康 | 127.0.0.1 | 仅本机健康检查 |
| 2379 | PD 客户端 | 127.0.0.1 | 仅本机管理 |
| 2380 | PD peer | 容器网络内 | 不发布 |
| 20160 | TiKV | 容器网络内 | 不发布 |
| 8300 | TiCDC | 127.0.0.1 | 仅本机 cdc cli |

> 现仓库 compose 把 2379/20160/10080 都发布到了 0.0.0.0。建议收敛为仅本地，减少暴露面；
> 4000 必须保持对外，因为 CDC sink 从对端连入。

## 4. 关键设计决策

### 4.1 为什么用“独立集群 + TiCDC”，而不是跨站 Raft

跨站 Raft 要求两站网络低延迟、稳定，且 2 节点无法形成多数派（需 3 副本跨站），
本环境只有 2 台机器，不满足。独立集群 + CDC 是两节点容灾的合理形态，代价是异步与 RPO > 0。

### 4.2 为什么 VIP 用宿主机 Keepalived，而不是 HAProxy

TiDB 只有两个固定后端，无需复杂负载均衡；Keepalived 直接维护 VIP，少一层组件和故障点。
Docker 已将 4000 发布到 `0.0.0.0`，VIP 流量经内核 DNAT 进入容器，无需额外配置。

### 4.3 为什么必须 unicast + nopreempt + 双 BACKUP

- **unicast**：本机既有容灾方案（`~/ha/replica`）使用单播，说明该网络多播不可靠。多播不通会导致双 master、VIP 冲突。
- **state BACKUP + priority 100/90**：初始选举按优先级选出 .27；`nopreempt` 只在 BACKUP 状态生效，因此两端都写 BACKUP。
- **nopreempt**：原主恢复后保持 BACKUP，VIP 留在当前主站，避免“数据旧的一侧被自动切回”。
- **健康检查脚本不配 `weight`**：脚本连续失败时节点进入 FAULT 并释放 VIP，备站因此能接管。
  若配置 `weight -20`，在两端都 `nopreempt` 的情况下，备站不会因为主站优先级下降而抢占，
  会导致 VIP 根本不漂移（本机既有 `~/ha/replica` 配置也是把 weight 注释掉的）。
- **启动顺序**：先启动 .27 的 keepalived，再启动 .28，确保初始 master 是 .27。
- 人工回切通过停/启 Keepalived 完成，不依赖优先级抢占。

### 4.4 数据同步方向与 TSO 锚点

```
正常态：  .27 TiCDC ──primary-to-secondary──▶ .28
故障后：  .28 TiCDC ──secondary-to-primary──▶ .27（sink 暂不可达，自动重试）
回切后：  .27 TiCDC ──primary-to-secondary'──▶ .28（以回切时刻 TSO 重建）
```

- 正向 feed 在故障期间随 .27 一起停止，不会产生回环。
- 反向 feed 的 `--start-ts` 必须是 **切换时刻的 TSO**，不能省略。省略只会同步“创建之后”的写入，故障窗口的数据会永久丢失。
- 若切换后超过 GC 保护期才建反向 feed，历史版本已被 GC，补齐会失败。因此要求：
  - 部署时通过初始化 SQL 把两站的 `tidb_gc_life_time` 设为 `24h`（见 5.4.1）；
  - 若遗漏，切换后立即经国产 SQL 客户端调整；
  - 反向 feed 必须在 GC 保留期内创建。

### 4.5 初始数据

- 推荐：两站清空数据目录，全新初始化，建 changefeed 后再灌业务数据。
- 若主站已有数据：先用 Dumpling/BR 全量导入备站，记录快照 TSO，再以该 TSO 创建 changefeed。
  本方案默认走“空库起步”，全量同步不纳入本次实施范围。

### 4.6 防双写

Keepalived 只能保证 VIP 单点，不能阻止直连 `:4000` 的写入。因此切换后必须：

- 停掉旧主站的 TiDB（`docker stop tidb-primary-sql`），或
- 网络层禁止应用直连旧主站 4000，或
- 在旧主站经国产 SQL 客户端设置 `SET GLOBAL tidb_super_read_only=ON`（重启后失效，需重新设置）。

推荐演练时直接停止旧主站 TiDB 容器，最简单可靠。

### 5.3 Keepalived 配置

`.27`（主站，priority 100）：

```conf
global_defs {
    # keepalived 2.2+ 执行脚本必须显式启用，否则报 SECURITY VIOLATION
    enable_script_security
    script_user root
}

vrrp_script check_tidb {
    script "/etc/keepalived/check_tidb.sh"
    interval 3
    timeout 2
    fall 2
    rise 1
    # 注意：不要配 weight。配了 weight 只会降优先级，
    # 两端都 nopreempt 时备站不会接管；不配 weight 则进入 FAULT 并释放 VIP。
}

vrrp_instance VI_TIDB {
    state BACKUP
    interface ens3
    virtual_router_id 51
    priority 100
    advert_int 1
    nopreempt
    unicast_src_ip 10.18.1.27
    unicast_peer {
        10.18.1.28
    }
    authentication {
        auth_type PASS
        auth_pass tidb123
    }
    virtual_ipaddress {
        10.18.1.100/24 dev ens3
    }
    track_script {
        check_tidb
    }
    notify_master "/etc/keepalived/notify.sh MASTER"
    notify_backup "/etc/keepalived/notify.sh BACKUP"
    notify_fault  "/etc/keepalived/notify.sh FAULT"
    notify_stop   "/etc/keepalived/notify.sh STOP"
}
```

`.28`：`unicast_src_ip 10.18.1.28`，`unicast_peer { 10.18.1.27 }`，`priority 90`，其余相同。

> 部署顺序：先启动 .27 的 keepalived，确认 VIP 在 .27 后再启动 .28。
> 如果先启动 .28，它会先成为 master，而 .27 因 `nopreempt` 不会抢回，初始状态就反了。

健康检查脚本 `/etc/keepalived/check_tidb.sh`：

```bash
#!/bin/bash
# 使用 TiDB/PD 自带的 HTTP 接口，不依赖 MySQL 客户端
set -u
# 1) TiDB 状态端口
curl -fsS --max-time 2 http://127.0.0.1:10080/status >/dev/null 2>&1 || exit 1
# 2) 本机 PD 健康
curl -fsS --max-time 2 http://127.0.0.1:2379/pd/api/v1/health >/dev/null 2>&1 || exit 1
# 3) 至少一个 TiKV store 为 Up（PD 返回带空格的格式化 JSON）
stores=$(curl -fsS --max-time 2 http://127.0.0.1:2379/pd/api/v1/stores 2>/dev/null) || exit 1
echo "$stores" | grep -Eq '"state_name"[[:space:]]*:[[:space:]]*"Up"' || exit 1
```

> 三项全通过才认为本站点可提供服务：TiDB 进程存活、PD 健康、TiKV 在 Up 状态。
> 这样 TiKV/PD 故障也会触发 FAULT 并释放 VIP，避免 VIP 停留在一个无法读写的站点。
> **不要安装/依赖 MySQL 软件包。**

`notify.sh` 只做日志与状态记录，不做任何数据提升动作：

```bash
#!/bin/bash
echo "$(date '+%F %T') $(hostname) -> $1" >> /var/log/keepalived-notify.log
```

### 5.4 TiCDC 配置

`config/cdc-config.toml` 保持 `filter.rules = ['*.*']`、`force-replicate = true`。
建 changefeed 时**不指定 `--start-ts`**，默认从当前 TSO 开始，避免 `0` 的语义歧义。

> `sink-uri` 中的 `mysql://` 是 TiCDC 对 MySQL 协议下游的固定 URI 方案，下游实际是 TiDB，
> 与 MySQL 数据库/客户端无关。root 密码由 TiDB 镜像 entrypoint 按 `TIDB_ROOT_PASSWORD` 初始化。

```bash
echo y | docker exec -i tidb-primary-ticdc /cdc cli changefeed create \
  --server=http://127.0.0.1:8300 \
  --sink-uri="mysql://root:123456@10.18.1.28:4000/" \
  --changefeed-id=primary-to-secondary \
  --config=/etc/cdc/cdc-config.toml
```

### 5.4.1 GC 保留时间（不依赖外部客户端）

`tidb_gc_life_time` 是 TiDB 系统变量，默认 `10m`。备站转为生产后，需要用切换时刻的 TSO
反向补齐，必须保证该 TSO 之后的 MVCC 版本没有被 GC。设置方式：

1. **首次初始化时自动设置（推荐）**
   - 在 TiDB 容器 entrypoint 生成的初始化 SQL 中追加：
     `SET GLOBAL tidb_gc_life_time='24h';`
   - 由 `tidb-server --initialize-sql-file` 自己执行，**不需要任何数据库客户端**。
   - 已用临时容器验证：该写法不会阻断 tidb-server 启动（`/status` 返回 200）；
     若目标环境启动日志出现初始化 SQL 失败，则退回第 2 种方式。
   - 实现方式见 5.5：新增 `scripts/tidb-entrypoint.sh`，在 compose 中只读挂载到
     镜像内的 `/entrypoint.sh`（不改镜像、不改 ENTRYPOINT）。
2. **已运行集群**
   - 使用单位统一的国产 SQL 客户端执行一次上述 SQL（本镜像未内置 Dashboard）。
3. **保持策略**
   - 演练期间保持 `24h`；本环境磁盘剩余 20G+，代价可接受。
   - 反向 changefeed 以切换 TSO 创建时，TiCDC 还会自动注册自己的 GC safepoint，
     与 24h 保留形成双保险。
   - 若确需恢复默认值，演练结束后经国产 SQL 客户端执行 `SET GLOBAL tidb_gc_life_time='10m'`。

## 6. 切换与回切流程

### 6.1 状态定义

| 状态 | VIP | 写入方 | 正向 CDC | 反向 CDC |
|---|---|---|---|---|
| 正常 | .27 | .27 | .27 → .28 | 无 |
| 故障中 | .28 | .28 | 停 | 无（等待原主） |
| 恢复中 | .28 | .28 | 停 | .28 → .27（补齐） |
| 已回切 | .27 | .27 | .27 → .28（新） | 已删除 |

### 6.2 故障切换（自动 + 人工）

**自动部分（Keepalived）**

1. .27 TiDB 不可用，连续 2 次（约 6s）健康检查失败
2. .27 进入 FAULT 状态，释放 VIP
3. .28 收不到 master 通告，成为 master，VIP `10.18.1.100` 漂移到 .28
4. 应用重连 VIP，写入落到 .28

**人工部分（在 .28 上执行 `scripts/failover.sh`）**

```bash
cd ~/mysql-cn/tidb-replica/scripts
sudo ./failover.sh
```

脚本依次完成：备集群健康检查 → 记录 `TSO_FAILOVER` 到
`/var/lib/tidb-dr/failover-tso` → 旧主可达则暂停其正向 feed → 校验 VIP 归属。
随后人工确认旧主已停止写入：

```bash
# 防止旧主继续接受直连写入（双写）
ssh sder@10.18.1.27 'docker stop tidb-primary-sql'
```

> 反向 changefeed 建议等 .27 恢复后再创建，避免 sink 不可达导致创建失败；
> 只要 GC 保留期内创建，`--start-ts=$TSO_FAILOVER` 即可补齐整个故障窗口。
>
> 若 .27 是整站宕机（不是只停 TiDB），第 3 步会跳过。恢复时不要直接 `up -d` 全量启动：
> 先启动 PD/TiKV，再启动 TiCDC 并第一时间 pause/remove 旧正向 feed，最后启动 TiDB，
> 否则旧 feed 可能把故障前未确认的尾部变更重放到已经是主的 .28。

### 6.3 恢复与回切（人工，建议低峰执行）

**第一步：恢复旧主并建立反向同步（在 .28 上）**

```bash
# 1. .27 恢复 TiDB（整站宕机过则先起 PD/TiKV，见 6.2 的注意事项）
ssh sder@10.18.1.27 'docker start tidb-primary-sql'

# 2. 建立反向同步；脚本自动读取 /var/lib/tidb-dr/failover-tso
cd ~/mysql-cn/tidb-replica/scripts
sudo ./recovery.sh

# 3. 确认 checkpoint 持续前进
docker exec tidb-secondary-ticdc /cdc cli changefeed query \
  -c secondary-to-primary --server=http://127.0.0.1:8300 --simple
```

**第二步：回切（在 .28 上，先停业务写入）**

```bash
# 0. 应用侧摘流量/停应用，确认 .28 不再有新写入
cd ~/mysql-cn/tidb-replica/scripts
sudo ./switchback.sh
```

`switchback.sh` 的固定顺序（不能颠倒）：

1. 记录回切位点 `TSO_CUT`；
2. 等反向 feed 的 `checkpoint` ≥ `TSO_CUT`，未追平则拒绝回切；
3. 删除反向 feed；
4. 在 .27 创建新正向 feed，`--start-ts=TSO_CUT`；
5. 停 .28 的 keepalived，VIP 回到 .27；
6. 重新启动 .28 的 keepalived（BACKUP，不抢占）。

> 关键点：`TSO_CUT` 必须在删除反向 feed **之前**记录，新正向 feed 必须先于
> VIP 回切创建。否则 VIP 已经回到 .27、写入已经开始，而正向 feed 还不存在，
> 这段时间的写入会丢失。
> 旧正向 feed 与反向 feed 必须全部删除后，再创建新的正向 feed，
> 否则两个方向的 feed 同时存在会形成复制回环。
> 停 .28 Keepalived 时，.27 会因收不到通告而成为 master，即使配置了 nopreempt 也会接管。

### 6.4 回切后一致性校验

以下为 **TiDB SQL**，通过单位统一的国产 SQL 客户端或业务应用执行，不使用 MySQL 客户端。
`mysql` 是 TiDB 为兼容而保留的系统库名，不是 MySQL 数据库。

```sql
-- 两端分别执行，比对结果
SELECT TABLE_SCHEMA, TABLE_NAME, TABLE_ROWS
FROM information_schema.TABLES
WHERE TABLE_SCHEMA NOT IN ('mysql','information_schema','performance_schema','sys')
ORDER BY 1,2;

CHECKSUM TABLE db.t1, db.t2;   -- 逐表比对
```

如需脚本化比对，使用 PingCAP 的 Dumpling 按主键顺序导出后计算哈希，
或用 TiCDC `changefeed query` 确认 checkpoint-ts 已追平当前 TSO。

关键表要求：行数一致、CHECKSUM 一致、抽样明细一致。

## 7. 一致性与数据保护

| 项目 | 方案 |
|---|---|
| 同步方式 | TiCDC 异步增量，正常态滞后通常 1–5s |
| RPO（故障瞬间） | 非 0，等于未落备站的尾部变更 |
| RPO（回切） | 追平后为 0 |
| RTO | VIP 漂移 6–10s + 应用重连，整体 ≤ 30s |
| 历史版本保护 | 部署时通过初始化 SQL 将 `tidb_gc_life_time` 设为 `24h`；反向 feed 以切换 TSO 创建时 TiCDC 还会注册 GC safepoint，双保险 |
| 重复变更 | 回切前删除旧正向 feed、以新 TSO 重建，避免重放冲突 |
| 系统库 | CDC filter 建议显式排除 `mysql.*`（TiDB 系统库）、`sys.*`，避免同步系统表 |
| 无主键表 | `force-replicate=true` 可同步，但下游可能产生重复行，要求业务表有主键/唯一键 |

## 9. 风险与限制

| 风险 | 影响 | 处置 |
|---|---|---|
| 站内单副本 | 任一 TiKV/PD 故障即整站不可用 | 接受，定位为容灾非高可用 |
| 健康检查覆盖不全 | TiKV/PD 故障但 TiDB 存活时 VIP 不漂移 | 已扩展为 TiDB `/status` + PD health + TiKV store Up 三项检查 |
| 无 fencing | 旧主直连可写，可能双写分叉 | 切换后停旧主 TiDB；演练流程强制检查 |
| 异步复制 | 故障瞬间丢尾部数据 | 接受；业务侧评估 RPO |
| GC 过期 | 反向补齐失败 | 部署时设为 24h；若遗漏，切换后立即经国产 SQL 客户端调大 |
| VRRP 多播不通 | 双 master、VIP 冲突 | 强制 unicast |
| VIP 自动回抢 | 流量切回旧数据 | nopreempt + 双 BACKUP + 人工回切 |
| 内存偏紧 | TiKV 默认 block cache 约占内存 45%，.27 还有 lumen 在跑 | 给 TiKV 限制 block cache，或容器内存上限 |
| 镜像被重建 | TiDB 退化为 mocktikv | 禁止用仓库 Dockerfile 重建，镜像只拉取 |
| 两站 root 弱口令 | 安全风险 | 仅内网；后续改密码并同步脚本/CDC sink URI |

## 附录 B：本方案与仓库现状的主要差异
