## 8. 下一步：keepalived + redis / mysql / etcd

### 8.1 先确认这些信息

- 主机、网卡、VIP 规划（每个服务一个 VIP，还是共用一个）
- 服务是宿主机进程还是容器
- 版本、端口、数据目录
- MySQL：主从复制方式（GTID?）、是否有 MHA/orchestrator
- Redis：主从还是 Sentinel/Cluster
- etcd：成员列表、是否已有 LB

### 8.2 可复用的东西

| 资产 | 复用方式 |
|---|---|
| `tidb-replica/scripts/deploy-keepalived.sh` | 改配置文件名即可用于新环境 |
| `tidb-replica/scripts/notify.sh` | 通用状态记录 |
| `tidb-replica/scripts/check_tidb.sh` | 健康检查模板，按服务替换探测命令 |
| keepalived 配置模式 | 双 BACKUP + nopreempt + unicast + 不配 weight |
| 部署/观测手册 | 步骤与观测方法可直接套用 |

### 8.3 三类服务的差异（关键）

| 服务 | 健康检查 | “升主”动作 | 建议 |
|---|---|---|---|
| MySQL | `mysqladmin ping` 或 `SELECT 1` | `SET GLOBAL read_only=OFF`、停复制/改指向 | keepalived 只搬 VIP，角色切换要 notify 脚本或 MHA/orchestrator |
| Redis | `redis-cli ping` | `REPLICAOF NO ONE` | 优先 Sentinel；keepalived 只搬 VIP，避免脑裂 |
| etcd | `etcdctl endpoint health` | 不需要（Raft 自选主） | VIP 只做客户端入口，慎用；建议 etcd gateway / LB |

**重要**：Keepalived 只负责 VIP 漂移，不会自动把 MySQL/Redis 升主。
如果只搬 VIP 不切角色，会出现“VIP 指向从库、写入失败/分叉”。

### 8.4 建议实施顺序

1. 先定 VIP 规划：**每个服务独立 VIP + 独立 `vrrp_instance` + 不同 `virtual_router_id`**，
   不要用一个 VIP 同时承载三个服务（一个服务故障会带着全部漂移）。
2. 每个服务先做健康检查脚本，手动验证成功/失败两种返回。
3. 单服务先做：MySQL（最成熟）→ Redis（考虑 Sentinel）→ etcd（评估是否真的需要 VIP）。
4. 每个服务单独演练：停服务 → VIP 漂移 → 角色切换 → 客户端验证。
5. 最后再考虑组合部署与资源分配。
